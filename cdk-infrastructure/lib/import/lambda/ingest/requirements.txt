# Dependencies for the s3-ingest Lambda layer. Pins came from the reference
# implementation (reference/dicomweb-s3/scripts/build_layer.sh), which built for
# Lambda Python 3.11 on manylinux2014_x86_64 — NOT the target here (PYTHON_3_14
# on manylinux_2_28), which is why the numpy pin had to move; see below.
#
# boto3/botocore are provided by the Lambda runtime and are deliberately
# NOT pinned here.
#
# tifffile + numpy back the SVS/BIF whole-slide ingest path (path_ingest.py):
# tifffile reads the TIFF/BigTIFF directory (IFDs, tile offset/bytecount
# arrays) over a ranged-S3 reader — structure only, never decoding pixels.
# numpy is tifffile's hard dependency.
#
# numpy is pinned to 2.4.6 to match lambda/dicom-encapsulator, NOT to 1.26.4 as
# the reference layer used. Two independent reasons, and the second is the hard
# one: the bundling command builds with
# `--platform manylinux_2_28_x86_64 --only-binary=:all:`, and numpy only began
# publishing manylinux_2_28 wheels at 2.3.0 - so 1.26.4 has no installable wheel
# here regardless of the Python version (verified: it fails identically under
# 3.12 and 3.14). The runtime is also PYTHON_3_14, and 1.26.x has no cp314 ABI.
#
# pydicom is pinned to 3.x for the same reason, from the other direction: the
# 2.4.4 inherited from the reference is the version NOTHING validates. The test
# suite is written against the pydicom 3 API (tests/conftest.py calls
# `save_as(..., enforce_file_format=True)`, a 3.x-only keyword) and passes on
# 3.0.2 under py3.14, so 2.4.4 could not even collect the suite, let alone be
# exercised by it. Pinning what the tests actually run closes a test-vs-Lambda
# version gap rather than opening one.
#
# pydicom and PyMySQL ship pure-Python (py3-none-any) wheels, so they install
# unchanged under cp314/manylinux_2_28.
pydicom==3.0.2
PyMySQL==1.1.3
tifffile==2024.8.30
numpy==2.4.6
