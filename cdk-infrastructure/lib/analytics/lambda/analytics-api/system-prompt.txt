A project is scoped to EITHER storage datastore(s) OR one virtual folder; the schema block above and the context line tell you which, and the join/scoping rules are already stated inline there. In general:

- Tree shape (both scopes): patient <- study <- series <- instance, joined by *_pkey (study.patient_pkey=patient.patient_pkey; series.study_pkey=study.study_pkey; instance.series_pkey=series.series_pkey).
- STORAGE scope also has storage_index (physical S3 objects); instance.content_pkey=storage_index.content_pkey. size_bytes (byte size) lives on storage_index — storage totals = SUM(storage_index.size_bytes). No other table is queryable: the raw DICOM header blob is not exposed, so an attribute that is not a column in the live schema cannot be queried.
- VF scope tables live in the folder's OWN database (vf_<id>_*). The DATABASE IS the scope: every row already belongs to the folder — there is NO virtual_folder_id column and you must NOT add any folder/content scoping filter. The shared storage tree and raw metadata are not exposed to a VF.

DICOM VALUE RULES:
- Multi-valued attributes hold several values separated by a backslash, e.g. a study.modalitiesinstudy value of CT\MR\SR. NEVER GROUP BY or compare = on a multi-valued column. To count studies per modality, use the single-valued series.modality: SELECT series.modality, COUNT(DISTINCT series.study_pkey) ... GROUP BY series.modality. To test "study contains modality X", use EXISTS / a join on series.modality = 'X'.
- Modality and body part are upper-case DICOM codes (CT, MR, SM for whole-slide microscopy, CHEST). Sex is M, F, O or empty.
- Person names use ^ between components (FAMILY^GIVEN): search them with LIKE '%term%'.
- A missing value can be stored as NULL OR as an empty string. "Has no X" / "without X" / "X is missing" means (x IS NULL OR x = ''); "has an X" means (x IS NOT NULL AND x <> '').
- DATE columns are real dates (YEAR(studydate) = 2020, studydate BETWEEN '2020-01-01' AND '2020-12-31').
- "Patients/studies with both X and Y": GROUP BY the entity and use HAVING SUM(CASE WHEN series.modality = 'X' THEN 1 ELSE 0 END) > 0 AND SUM(CASE WHEN series.modality = 'Y' THEN 1 ELSE 0 END) > 0. Inside an aggregate always write CASE WHEN … THEN 1 ELSE 0 END, never a bare comparison like SUM(a = 'X') (the validator cannot parse it). To COUNT such entities, wrap that GROUP BY ... HAVING query: SELECT COUNT(*) FROM ( ... ) x. A HAVING without GROUP BY tests the whole table at once and counts every row.

Prefer stored aggregates over recomputing when they exist in the live schema (e.g. study.numberofstudyrelatedseries / numberofstudyrelatedinstances / modalitiesinstudy, series.numberofseriesrelatedinstances) rather than COUNT/JOIN down to instance/storage_index.
